# Zoom-Out Review — REACH Compliance Copilot POC

*Goldfish: Skeptical Architect (zoom_out). Inputs: `concepts_brief.md`,
`docs/designs/reach-compliance-copilot.md`. Mode: REVIEW.*

## Overall

The design is unusually disciplined for a POC: the division of labor
(model does language, Python does math) is correct, the non-goals in §1
are real non-goals, and §6's "known weak points" section is the right
instinct. The core architecture — 4B resolver + deterministic SQLite
pipeline + honest eval table — is the right shape and I would not
redraw it.

The problem is that the one thing the POC exists to prove — "the 4B
matches the big LLM at a fraction of the cost" — rests on an eval
harness that is under-specified exactly where it matters: no accuracy
bar, no ground-truth methodology, and a circular teacher/judge
relationship. The POC's success criterion (§1: "the eval table exists
and is honest") is currently unfalsifiable.

---

## Findings

### 1. The eval bar is never stated — the success criterion is unfalsifiable
- **Severity**: Blocker
- **Affected Scope**: §1 (success criteria), §7 (eval harness); brief open question 5
- The brief explicitly flagged this as open ("within X points" vs
  "statistically indistinguishable"), and the design — which is supposed
  to be the build specification — leaves it open. "Within a small,
  stated margin" (§1) is a margin that is never stated. Without a number
  (e.g., "≥90% exact-match on EC number, within 5 points of the cloud
  LLM on the same held-out set, n≥200"), the three-number table in §7
  can show anything and prove nothing, and the Substack post has no
  claim to make. Define the bar before building `eval/run_eval.py`, not
  after.

### 2. Teacher–student circularity in the eval
- **Severity**: Blocker
- **Affected Scope**: §3 (Task A training labels), §7 (eval reference)
- Training labels are generated by "a cloud big LLM" and the eval
  compares the 4B against "cloud big LLM" — the same model, playing
  teacher and judge. Two consequences:
  1. The student can never beat the teacher, so "accuracy close to the
     cloud big LLM" is partly self-fulfilling: the 4B is being measured
     against the model that wrote its homework.
  2. Label validation (§3: "the emitted EC/CAS must exist in the ECHA
     data or PubChem") checks *existence*, not *correctness*. A name can
     map to a valid-but-wrong EC number and pass validation.
- The held-out set (≥200 resolution items, §7) must be **human-verified**
  ground truth, independent of the teacher. That is real work and it is
  missing from the build order (§9). Add it as an explicit step with an
  owner and a date, because the entire public claim of the POC hangs on
  it.

### 3. Task B is a YAGNI violation the design already half-admits
- **Severity**: Major
- **Affected Scope**: §2 (step 4), §3 (Task B), §6.4, §9 (step 6)
- The design states in §3 that Task B "is mostly deterministic," that
  "the deterministic rules in step 3 are the source of truth and the
  report cites them, not the model," and that model/rule disagreement is
  "an eval signal, not a runtime branch." So at runtime, Task B's output
  is discarded except for a plain-language summary line. The stated
  justifications for fine-tuning it — (a) a summary line, (b) "be the
  thing we fine-tune and eval" — are showcase garnish, not the claim the
  POC exists to prove. §6.4 already concedes it drops out if it
  interferes; §9 already defers it to step 6.
- Recommendation: cut Task B from the POC scope entirely (move it to a
  "stretch / next" note). One task, one adapter, one eval. This removes
  the task-interference risk (§6.4), halves the data-generation work in
  §5, and removes the `use context` field's only consumer (see finding 6).
  The plain-language summary line can be produced by a template in
  report.py — deterministic, citable, zero model risk.

### 4. Confidence/abstention is asserted, not designed
- **Severity**: Major
- **Affected Scope**: §2 (step 1), §3 (Task A output), §7 ("abstention calibration")
- The brief's working assumption is that abstention is the credibility
  feature. The design implements it as a free token
  (`confidence: high|medium|low`) the model emits, and §7 lists
  "abstention calibration" as an eval output — but nothing in the design
  produces calibrated confidence. A 4B's self-reported "high" is not
  calibrated by virtue of being in the prompt. There is no mechanism
  (logprob threshold, temperature, calibration set, mapping rule from
  token → route). Decide the mechanism: simplest viable option is
  "model says low/medium → needs_review" plus a calibration check in
  eval (of items labeled low, what fraction were actually wrong?). As
  written, the needs_review path in the demo BOM (§4: "1 ambiguous name")
  demonstrates the plumbing, not the policy.

### 5. "Fraction of the cloud cost" has no methodology
- **Severity**: Major
- **Affected Scope**: §1, §7 (cost-per-1k-calls)
- Cost-per-1k for the 1660 is undefined: amortized hardware?
  electricity? hours-of-use? The cloud side is per-token pricing.
  Apples-to-oranges numbers in a public table invite the exact
  skepticism the POC is trying to answer. State the methodology in the
  design (e.g., "1660 fully amortized at $X over Y months + power at
  $Z/kWh, vs. cloud list price per 1k calls at observed token counts").
  Also: the cloud LLM is never named anywhere in either document. For a
  public repo and post, model identity, prompt, and pricing are part of
  reproducibility. Name it.

### 6. `use context` is a dead field if Task B is cut — and weak even if kept
- **Severity**: Major (if Task B kept) / Nit (if cut)
- **Affected Scope**: §2 (BOM schema, step 3), §3 (Task B input)
- The deterministic rules in step 3 never consume `use`: SVHC is
  concentration-only, XIV is "any use," XVII is flag-and-quote. The only
  consumer of `use` is the model in Task B — the task most likely to be
  dropped. If Task B stays, the design should say what `use` values
  exist in the training distribution and how they change labels; as
  written it's an unstructured free-text column feeding a classifier
  with no specified semantics.

### 7. The 1660 fit is asserted, not verified
- **Severity**: Major
- **Affected Scope**: §5 (serving), brief (8–16K context)
- 4.3GB Q8_0 weights + 8K KV cache + runtime overhead on 6GB VRAM is
  tight, and the design asserts it without a verification gate. Also
  unaddressed: Qwen3 is a hybrid thinking model — thinking-mode tokens
  consume context and latency, which directly hits the latency-per-1k
  number in §7. The design should (a) make "model serves and answers on
  the 1660 at 8K ctx" an explicit gate at the end of build-order step 3,
  and (b) state whether thinking mode is on or off and why (off is the
  defensible POC choice for latency; say so).

### 8. "Reproducible from a clean clone" vs. data provenance
- **Severity**: Major
- **Affected Scope**: §1 (success criteria), §4 (data)
- The ECHA CSVs were captured by clicking a button in headless Chromium
  (`src/fetch_echa.py`) — a brittle scraper. The design never says
  whether the CSVs are committed to the repo (they exist locally in
  `data/`). If committed: state it, and note that ECHA lists change
  (SVHC is updated ~twice yearly), so the report's "date" citation
  depends on pinning the list version — the `metadata` table in
  `reach.db` exists but the design doesn't mention using it. If not
  committed: "reproducible from a clean clone" is false on day one.

### 9. The demo proves less than the success criteria imply
- **Severity**: Major
- **Affected Scope**: §1 (non-goals: "resolution pre-verified"), §4 (demo BOM), §9 (step 1)
- Build-order step 1 produces "first correct cited report" with a **stub
  resolver** on a **pre-verified** BOM. That report is correct by
  construction — it validates the deterministic core (good), but the
  success criterion "the demo BOM produces a correct cited report" is
  therefore satisfied before any model exists. The only artifact that
  carries the actual claim is the eval table — which is finding 1 and 2
  territory. This isn't a flaw in the plan, but the design should say
  plainly: *the demo demonstrates the pipeline; the eval demonstrates
  the claim.* Right now §1 blends them.

### 10. Repo layout drift
- **Severity**: Nit
- **Affected Scope**: §8 vs. actual tree
- Target layout is `src/reach/` package; the existing code is flat
  (`src/ingest.py`, `src/fetch_echa.py`, `src/debug_echa.py`). The design
  doesn't mention migrating the existing scripts, and `debug_echa.py`
  (a debug script) has no home in the target layout. One sentence:
  "existing scripts move into `src/reach/ingest/` (or stay at top level
  as tooling); debug_echa.py is deleted before the repo goes public."

### 11. The "list-diff script" is a dangling commitment
- **Severity**: Nit
- **Affected Scope**: §1 (non-goals)
- "The continuous monitoring story is told with a list-diff script, not
  a service" — this script appears nowhere else: not in the pipeline
  (§2), not the repo layout (§8), not the build order (§9). Either add
  it to the build order (it's small and cheap) or cut the sentence.

### 12. Training data distribution is unspecified
- **Severity**: Nit
- **Affected Scope**: §5 ("~2–5K training examples"), §3 (Task A labels)
- 2–5K generated examples from what name distribution? If the teacher
  generates names from PubChem synonyms, the training distribution is
  PubChem-shaped, while the eval set (finding 2) should be
  BOM-shaped. State the generation recipe (source of names, noise
  model, dedup) at one-paragraph altitude — enough that the train/eval
  distribution relationship is a design decision, not an accident.

---

## What's good (don't fix)

- The model/deterministic split (§2) is the correct architecture and the
  design resists the temptation to let the model do math.
- C&L deferral (§4) is the right YAGNI call; the brief's open question 3
  is resolved correctly.
- PubChem as training-time-only (§4) resolves brief open question 4
  cleanly.
- §6's honesty about curated-set numbers is exactly the posture the
  public post needs.
- No premature infrastructure: no queues, no services, no UI, SQLite.
  The sibling use-case repos are docs-only, so the "reuse across five
  use cases" claim is aspirational but not yet a reuse burden — REACH
  genuinely is the first build.

## Verdict

**NEEDS-WORK.**

The architecture is sound and the scope is mostly right. Before build:
(1) state the accuracy bar and make the held-out set human-verified
(findings 1–2), (2) cut Task B from POC scope (finding 3), (3) define the
confidence mechanism and cost methodology (findings 4–5), (4) add the
1660 smoke test as a gate and state thinking-mode policy (finding 7),
(5) state data provenance/pinning (finding 8). Findings 10–12 are
one-paragraph fixes. None of this changes the shape of the system.
